## 二、设计合理性

当前结构“轻量 Logger → 有界异步目标 → FDBus 适配 → 单线程汇聚排序 → 两类 Sink”职责清楚。过滤放在产生端，动态控制经 FDBus 更新原子阈值，合理减少无效记录与传输。

共享 FIFO、共享重排器和退出时全局屏障是符合工期与题目范围的简化。业务进程正常运行无需周期发送 flush，当前演示在生产结束收尾时调用。某个 worker 退出时会提前释放其他来源的缓存，属于需要说明的跨窗口乱序边界，不据此要求重写进程级缓冲或 flush。

全局汇聚错误/丢弃计数不能解释为某个 worker 独有统计。flush 只确认屏障前已接受记录的约定输出与 stream 刷新，不是 fsync 或掉电保证；主汇聚 shutdown 最后的 join 也不保证固定总时限。这些是语义边界，不应通过增加复杂系统来掩盖。

## 三、需要修复的问题

以下 P1 优先于 P2，P3 为后续整理。证据强度分别注明；所有问题当前均未修复。修复时先处理影响必需功能和可信验收的缺陷，再考虑代码精简。

### F1 [P1] 关闭时可能跳过已接受、尚在 FIFO 的日志

位置：[src/log_aggregator.cpp:170](../src/log_aggregator.cpp#L170)，重点 170–174；关闭队列在 146–149，退出末尾在 208–209。

可触发时序：

1. 消费线程 waitPopFor 超时，进入 outputReady(false)，输出先前缓存时在 Sink 内阻塞。
2. 另一线程成功提交新记录，随后调用短超时 shutdown。
3. shutdown 内 flush 超时后执行 queue.close。
4. Sink 恢复，消费线程只判断 closed 就 break，没有再次取 FIFO。
5. 末尾仅排空重排缓存；新入队记录仍留在 FIFO。

影响：记录已经 counted accepted，却未输出，也没有进入 dropped/rejected；违背关闭后排空及受控丢弃计数的要求。根因是“超时判空”和“检查关闭”分离，closed 不等于关闭且排空。

最小方向：让 pop 在同一把锁下区分“有数据／超时／关闭且空”，或关闭后继续取完已有数据；不能仅凭 closed 退出。

验证建议：用可控阻塞 Sink，精确安排上述时序，核对 accepted 记录最终全部输出或有明确损失计数。证据：静态确定执行路径，未编译运行该 C++ 竞态复现。

### F2 [P2] 字节截断会破坏合法中文 UTF-8

位置：[src/logger.cpp:54](../src/logger.cpp#L54)，54–55；proto/log_protocol.proto 的 module/message 为 string。

默认上限下，43 个“中”为 129 字节，截到 128 后末尾是不完整编码；1366 个“中”为 4098 字节，截到 4096 同样破坏编码。

影响：本地输出出现破损文字；跨进程路径把不符合 UTF-8 契约的内容写入 proto3 string，存在整条日志被解码拒绝的风险。

最小方向：字节上限不变，但截在完整 UTF-8 码点边界，并保留 truncated 计数；不要为修复这个问题引入通用文本框架。

证据：对与源码相同的字节切片进行严格 UTF-8 解码，两项均失败；尚未运行当前 C++ Protobuf 3.21.12 链路。验证应覆盖上限前后中文/英文混合模块名及正文。

### F3 [P2] 演示脚本吞掉服务端错误退出，可能假报成功

位置：[scripts/run_demo.sh:38](../scripts/run_demo.sh#L38)，服务端 wait 后使用 || true；最终退出沿用进入 cleanup 前的状态。

触发：两个 worker 均以 0 退出，但 server 在关闭时发现写入/刷新错误并以 2 退出。脚本忽略 server 的 wait 结果，仍以 0 结束；控制演示依赖本脚本，也受影响。

影响：失败演示可能被记录为成功，不能据此验收文件输出和退出可靠性。

最小方向：收集关键子进程退出状态；保留原始失败原因，同时把原本成功路径上的服务端收尾失败变成非零结果。正常预期的信号退出需要与真实错误区分。

证据：使用 Git Bash 执行当前原始 run_demo.sh，以临时短时进程替代 SDK/server/worker。server 明确输出错误并 exit 2，两个 worker exit 0，脚本实际 exit 0。该测试证明脚本状态传播缺陷，不等于真实 FDBus 链路已运行。

### F4 [P2] 尚未实际绑定，就宣布服务启动成功

位置：[src/log_server.cpp:167](../src/log_server.cpp#L167)，167–183；apps/log_server_main.cpp:239–242。

触发：重复启动相同服务名，或 name_server 尚不可用。当前 start 发起异步 bind 后立即返回 true，应用打印 bound/listening；实际登记可能失败。

影响：用户会把未就绪或无法登记的进程当成可用服务，排查不到日志时被错误状态误导。

证据：追踪自带 SDK，svc:// 的 bind 先请求地址，实际注册异步完成；name_server 拒绝重复服务名，内部代理处理该结果，当前应用没有取得就绪结果。SDK 依据为 CBaseServer.cpp:176–183、CNameServer.cpp:526–529 和 CIntraNameProxy.cpp:590–604。不是看到 bind 返回 invalid 就认定失败；正常 svc 流程也可能返回该值。未实测双 server 场景。

最小方向：区分“发起登记”和“服务实际可用”，取得实际绑定就绪/失败状态并有界等待，再决定 start 的成功和 listening 提示；不能直接检查 bind 返回 ID 作为修复。

### F5 [P2，次要边界] 已有文件可写不可读时，轮转漏算原有大小

位置：[src/rotating_file_sink.cpp:62](../src/rotating_file_sink.cpp#L62)，62–64。

触发：Linux 上已有日志文件对当前用户仅可写不可读。ifstream 获取大小失败，current_bytes 留为 0；append 打开却能成功，已有文件内容没有计入阈值。

影响：重启后即使文件已超阈值仍继续追加，直到新增字节达到阈值才切割。

最小方向：使用文件 stat 的 st_size 获取原有长度，仅 ENOENT 视为新文件，其余错误如实处理。可同时省去一次文件读取打开。证据：静态权限与控制流推演，未做 Linux 权限实测。

## 四、较低优先级的简洁性与接口边界

### F6 [P3] 无符号参数解析接受负数

位置：[apps/app_support.h:62](../apps/app_support.h#L62)。

number 使用 strtoull，仅检查 errno 和尾随字符，没有拒绝负号。例如 --count -1 可变成极大的无符号计数，导致演示长时间不结束。应在转换前明确参数允许的十进制格式，按参数语义校验范围；无需扩展复杂命令行框架。证据：静态控制流及 C 运行时同类无符号解析函数测试，未运行 Ubuntu 应用参数用例。

### F7 [P3] 退出收尾重复发送 flush

位置：[apps/log_worker_main.cpp:51](../apps/log_worker_main.cpp#L51) 与 57；[src/fdbus_transport.cpp:346](../src/fdbus_transport.cpp#L346)。本地演示也先显式 flush 再 shutdown。

影响：退出重复屏障及等待，检查的是第一次结果而关闭内部再次 flush 的结果被忽略。不是平时频繁 flush，也不是必需功能缺失。

方向：保留一个能停止新生产、完成排空并返回结果的清晰收尾入口；如果保留独立 flush，明确如何避免无意义的重复。不要简单删除退出可靠性处理。证据：当前调用链静态核对。

### F8 [P3，当前演示未触发] 异步完成回调缺少重入约束

位置：[src/log_aggregator.cpp:201](../src/log_aggregator.cpp#L201)，201–204；shutdown 的 join 在 149。

flushAsync 回调运行在汇聚消费线程。外部调用者若在回调内同步 flush，会等待自己；若调用 shutdown，则超时后可能 self-join 抛错，异常被吞后线程仍 joinable，后续析构可能 terminate。

当前服务端回调只有回复和计数，不触发此路径。至少注明回调线程与禁止同步关闭/等待的契约，并在改变关闭状态前检测非法线程；若支持回调发起关闭，由外部线程完成 join。证据：静态 API 边界推演。
