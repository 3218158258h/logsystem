FDBus：发现、直连与消息调度

连接如何建立

  • 名字服务：log_server 注册服务名；客户端订阅并获得地址。
  • Session：业务进程直连日志服务；日志与控制复用会话。
  • 传输层：本地可用 Unix 域 socket，跨机使用 TCP。

消息如何流转

  • Protobuf：发送端编码记录，接收回调解码并校验。
  • Context / event loop：调度在线、离线、请求与回复回调。
  • 线程分工：回调只校验、入队和应答；发送与输出各有后台线程。

有限窗口排序与统一输出

释放记录的条件

  • 时间水位：最大已见时间戳减去窗口，默认 50ms。
  • 输入空闲：默认 100ms 后释放积压；退出时释放剩余。
  • 容量兜底：超过 4096 条时提前释放最早记录。

统一输出

  • 按时间戳及辅助键排序；迟到记录照常输出并计数。
  • 输出前才格式化，统一写控制台与轮转文件。
  • ERROR → stderr，其余 → stdout；文件默认 5MB、3 份备份。

IPC 与远程收集方案对比
方案适用与收益实现、可靠性与运维成本
FDBus / 本地 socket当前采用：名字服务、会话、消息调度由 SDK 管理业务仍负责队列、错误统计和退出；本地连接与部署较简单
直接 socket适合希望完全掌控协议和数据通道的场景自行实现发现、分帧、重连与超时，维护成本更高
共享内存适合大批量数据交换，可减少跨进程复制同步、缓冲区归属、满队列与崩溃恢复更复杂
本地文件 / 远程收集本地直接写出；远程便于多机统一检索与留存网络增加延迟与失败点；还需缓冲、去重、鉴权加密及收集端运维
代码 / 依据：题目 §2.3、A级方案对比；SDK CNameServer；src/client/fdbus_transport.cpp · Client

AI 协作：方案否决与缺陷纠偏

人主导：纠正退出方案

  • AI 方案：将“退出时 flush”扩展成远程请求与队列屏障。
  • 人的追问：业务进程为何能提前冲刷其他来源？题目是否需要？
  • 修正：移除跨进程 flush；保留各端 shutdown 和内部输出收尾。

历史缺陷：陈旧日志判断就绪

  • 位置 / 根因：旧控制脚本用残留 worker-a 文本判就绪，过早发送 list。
  • 修正：清空旧输出，等待本轮 A/B 两个来源后再查询。
  • 历史验证：用户回传调级与收尾成功；accepted=307，dropped=0，write_errors=0。

成长与计划
实习成长
  • 通信机制理解：从“name_server 转发消息”的误解，转向区分服务发现与客户端到 log_server 的直接会话。
  • 需求与设计判断：发现业务 flush 会影响共享重排缓存，回到“退出时 flush”的要求，决定移除跨进程控制入口。
